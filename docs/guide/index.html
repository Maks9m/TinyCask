How TinyCask keeps your data, and why every piece is there

TinyCask is a key-value database built like Bitcask: every write goes to the end of a file, and a hash map in memory remembers where the newest value of each key lives. This page explains how it is built, section by section, and lets you break a working model of the database in your browser.

  1. Read chapters 1–5. They give you the vocabulary everything else uses.
  2. Play with the simulator in chapter 2. Write, crash, compact and corrupt it.
  3. Dip into the rest in any order. The glossary links every term back to its chapter.

01§1 System overview

The big idea

A key-value store is a dictionary that survives a restart. You PUT user=ann, the machine reboots, you GET user and get ann back.

Two requirements pull in opposite directions. To survive a restart, data must be on disk, and disk is slow. To be fast, lookups should happen in memory, and memory forgets everything when the process dies. TinyCask splits the job in two:

  • The log, on disk, holds the data. It is append-only: a new value is always written at the end of a file, and nothing already written is ever changed.
  • KeyDir, in memory, holds the index. For every key it stores which file and which byte offset contain the newest value.

Think of a notebook in which you only ever write on the next empty line and never erase. A sticky note on the cover says on which line each name's latest entry is. Reading is fast: look at the sticky note, open the line. Writing is fast: always the next line. If the sticky note is lost, you rebuild it by reading the notebook from the first line to the last. That rebuild is crash recovery.

Why append-only

  1. Speed. Writing at the end needs no search for a free place. Sequential writes are the fastest thing a disk does.
  2. Safety. Old data is never overwritten, so a crash in the middle of a write can only damage the last few bytes of the newest file. Everything before them is untouched.
  3. Simplicity. No free-space management, no update-in-place logic, no page splits.

What it costs, and what TinyCask does about it

CostTinyCask's answer
Overwritten and deleted values keep taking disk space.Compaction copies only live records to a new file and deletes the old files (chapter 8).
Every key must fit in RAM.Accepted, and a stated non-goal. One million keys need about 100–150 MB (chapter 5).
Startup reads every file to rebuild KeyDir.Accepted for v1. Real Bitcask adds hint files to speed this up; out of scope here.
No range queries ("all keys starting with user:"): a hash map has no order.Out of scope.

Where the design comes from

Justin Sheehy and David Smith described Bitcask in 2010 as the storage engine of the Riak database (company: Basho). TinyCask follows that design closely. Every part of it comes from a published design that ran in production.

Why this way

"Why not keep everything in a Go map and save it to a file when the program exits?"

A crash or power cut before the save loses everything since the last save. With the log, each write reaches the operating system before the client gets OK, so a process crash loses nothing that was acknowledged.

What happened newest first

    Simulator limits: keys up to 12 bytes, values up to 24 bytes, files roll at 128 bytes. The real defaults are 1 KiB, 1 MiB and 64 MiB. File names are shortened (seg_3.data instead of seg_0000000003.data). It loads with five example writes so there is something to look at.

    Try this

    1. PUT user three times with different values. Older versions fade: they are garbage. KeyDir points only at the newest.
    2. DELETE user. A dark tombstone is appended and the key leaves KeyDir. The old values are still on disk.
    3. Keep writing until the active file fills up. It becomes sealed and a new file becomes active.
    4. Press Crash mid-write, then Restart. Recovery cuts off the torn record and the previous value is back.
    5. Press Start under Compaction, then step to 3/5. Now PUT a key that exists. At step 4 that key is "left alone".
    6. Start a compaction, step past 3/5 (rename), press Crash, then Restart. Recovery deletes the old files because the output supersedes them.
    7. With two or more files, press Bit rot in an old file, then GET the damaged key (the log names it). You get ErrCorrupt, never a wrong value.
    8. Now DELETE that key and press Restart. The database still refuses to open, although the key is gone. That is fail-stop; chapter 7 explains why deleting doesn't help.
    03§3.1 Record

    A record, byte by byte

    Every PUT and DELETE becomes one record appended to the active file. The design doc calls it a frame. A record is a 21-byte header followed by the key and the value.

    BytesFieldSizeWhat it is for
    0–3CRC324Checksum of bytes 4 to the end of the record. Detects torn writes and bit rot.
    4–11Timestamp8Nanoseconds since 1 Jan 1970 (Unix epoch). For people and debugging only.
    12Type11 = PUT, 2 = DELETE (tombstone). Any other value means corruption.
    13–16Key size4Key length in bytes, 1–1024.
    17–20Value size4Value length in bytes, 0–1 MiB. Always 0 for a tombstone.
    21…KeyKThe key bytes.
    21+K…ValueVThe value bytes.

    21 = 4 + 8 + 1 + 4 + 4. Edit the key and value below and watch the bytes change. Then click any byte to flip one bit, the way a failing disk would, and see which check catches it.

    Timestamp fixed at 2026-11-19 12:00:00 UTC. The default record's bytes match a Go program that uses encoding/binary and hash/crc32, byte for byte.

    Little-endian

    A number bigger than one byte has to be split into bytes, and the format must fix their order. Little-endian puts the least significant byte first: the key size 4 is stored as 04 00 00 00, and 258 (hex 0x0102) as 02 01 00 00. x86 and ARM processors, your M1 included, work in little-endian, but the real point is that the order is fixed forever, so a file written on one machine reads the same on another. In Go: binary.LittleEndian.PutUint32(buf[13:17], uint32(len(key))).

    CRC32

    A checksum is a short fingerprint of some data. CRC32 turns any number of bytes into a 32-bit number in a way that guarantees a different result for any single flipped bit and for any burst of damaged bits up to 32 bits long. On write we compute it over bytes 4 to the end and store it in bytes 0–3. On read we compute it again and compare. If they differ, the record is torn or rotted, and the engine returns ErrCorrupt instead of wrong data.

    CRC is not cryptography: it catches accidents, not attackers. "IEEE" names the polynomial, the same one Ethernet and ZIP use; in Go it is crc32.ChecksumIEEE.

    Why each field is there

    • Type byte instead of "value size 0 means deleted". Version 1.0 of the design doc marked deletes with value size 0. Then PUT k "" (an empty value) and DELETE k would look the same on disk. A separate type byte keeps empty values legal. This is correctness fix 2 in the design doc's change log.
    • The CRC also covers the key, and GET compares the stored key with the requested one. If a bug made KeyDir point at a different record, that record's CRC could be valid, but the key check catches it.
    • The timestamp never decides which version wins. Wall clocks jump: NTP corrections, manual changes, virtual machines. Ordering by time could bring back an old value. The position of a record, (file ID, offset), is the exact order of writes. The timestamp stays because the approved design has it, and it helps when you read a dump.
    • Lengths are checked before anything is allocated. A damaged header might say the value is 4,000,000,000 bytes. Code that trusts it would try to allocate 4 GB and die. So the decoder checks, in order: enough bytes for a header, a known type, sizes within limits, enough bytes for the payload, and only then the CRC. The fuzz test FuzzDecodeRecord exists to prove this holds for any input.

    Offsets: where things are

    An offset is a byte position in a file, counting from 0. KeyDir stores ValueOffset, where the value starts, because that is the struct the approved design doc defines. GET needs the whole record to check the CRC, so it computes the record's position:

    RecordOffset = ValueOffset - 21 - len(key)
RecordSize   = 21 + len(key) + ValueSize

// user=bob written at offset 57 (Figure 1):
// ValueOffset  = 57 + 21 + 4 = 82
// RecordOffset = 82 - 21 - 4 = 57
// RecordSize   = 21 + 4 + 3  = 28
    Why this way

    "What happens if the power fails in the middle of writing a record?"

    Only the end of the newest file can be incomplete. Recovery reads it, sees that the record is shorter than its header promises or that its CRC does not match, cuts it off and continues. That write never got an OK, so nothing acknowledged is lost.

    04§3.2 Data directory

    Files on disk

    The log is not one endless file. It is split into segments, files of up to 64 MiB. Only one segment, the active one, receives writes. When it is full it is sealed (also called immutable): fsynced and never written again. A new active segment is created. This is called a roll or rotation.

    data/ ├── LOCK # held by the running process ├── compact_0000000004.data # output of a compaction, replaced seg 1–3 ├── seg_0000000005.data # sealed └── seg_0000000006.data # active: the only file being written
    FileMeaning
    seg_<id>.dataA regular segment. The highest ID is the active segment.
    compact_<id>.dataCompaction output. Supersedes (replaces) every data file with a lower ID.
    compact_<id>.tmpA compaction that never finished. Deleted at startup.
    LOCKProof that one process owns the directory.

    Why segments at all

    You cannot delete the beginning of a file. One endless file would only ever grow. With segments, compaction can delete whole old files and the disk space really comes back.

    Why IDs, and why 10 digits

    Every file gets a number, its file ID, and IDs only grow. The ID gives the order of the files: lower ID means older data. IDs are uint32, so at most 4,294,967,295, which has 10 digits. Zero-padding to 10 digits makes alphabetical order equal numeric order: seg_0000000009 sorts before seg_0000000010, while seg_9 would sort after seg_10. Gaps in IDs are normal, for example after an unfinished compaction.

    The supersede rule

    "compact_M.data supersedes every data file with an ID below M." Compaction always merges all older files into one output with ID M. If the process dies after the output is in place but before the old files are deleted, recovery sees the output and deletes the old files itself. One naming rule replaces a separate manifest file that would otherwise have to list which files are valid.

    The LOCK file

    The engine takes an exclusive flock on LOCK. flock is an advisory lock provided by the operating system: only one process can hold it, and the kernel releases it automatically when the process dies, even after kill -9. Without it, two TinyCask processes on the same directory would both append to the active file and mix their records into garbage. "Advisory" means it only stops programs that ask for the lock; a plain shell command would ignore it.

    Why this way

    "Why does compaction delete the old files last, not first?"

    If the process died between "delete old files" and "make the output official", the data would exist nowhere. The order is: make the output durable and official, then delete. At every moment at least one complete copy of the data is valid on disk.

    05§4 In-memory data model

    What lives in memory

    KeyDir is a Go map from key to a small struct, protected by a read-write lock. The struct is exactly the one from the design doc:

    type CommandIndex struct {
    FileID      uint32 // which file holds the newest record
    ValueSize   uint32 // value length in bytes
    ValueOffset int64  // where the value starts inside that file
    Timestamp   uint64 // informational only
}

type KeyDir struct {
    mu    sync.RWMutex
    index map[string]CommandIndex
}

    The map key is a string, not a []byte. Go does not allow slices as map keys (they cannot be compared with ==), and converting []byte to string copies the bytes, so the caller can reuse its buffer without corrupting the index.

    MethodWhat it doesWho uses it
    Get(key)Returns the entry, or "not found"GET, compaction's liveness check
    Put(key, e)Sets the entry, returns the previous onePUT, recovery
    Delete(key)Removes the entry, returns the previous oneDELETE, recovery
    Len()Number of live keysStats, invariant checks
    UpdateIf(key, cond, new)Replaces the entry only if cond(old) is true, atomicallyCompaction's conditional swap (chapter 8)

    KeyDir never touches the disk. It only answers "where is it?". Keeping it free of I/O keeps its lock short, and it can be tested on its own under the race detector.

    Two counters and the garbage ratio

    • liveBytes: total size of the records KeyDir points at. Changes when KeyDir changes.
    • diskBytes: total size of all data files. Changes when files grow or are deleted.
    • Garbage ratio = 1 − liveBytes / diskBytes. Example: 100 MB on disk, 40 MB live → 0.6. That is at least 0.5 and the disk holds at least 16 MiB, so automatic compaction starts.

    How much RAM

    The design doc's estimate is N × (len(key) + 48 bytes): roughly 16 bytes for the string header, 24 bytes for CommandIndex (4 + 4 + 8 + 8), and a few bytes of map bookkeeping. For one million 32-byte keys the formula gives 80 MB. Go's map adds more overhead, which is why the target says 100–150 MB and a benchmark measures the real number instead of trusting the formula.

    Why this way

    "What if the keys don't fit in memory?"

    Then this design is the wrong tool, and the design doc says so as a non-goal. Bitcask makes the same trade. An LSM tree such as RocksDB is the usual choice when the index cannot fit in RAM.

    06§5.1–5.3 Put, Get, Delete

    Writing and reading

    PUT, step by step

    1. Check sizes and encode the whole record into one buffer.No lock yet: encoding takes time and touches no shared state, so it would only make other writers wait.
    2. Take the writer lock.
    3. Refuse if the engine is read-only or closed. Roll if the record does not fit.Roll = fsync and seal the active file, create the next one, fsync the directory.
    4. Append the record with a single Write call.On an error or a short write: truncate the file back to its previous size. If even that fails, switch to read-only mode.
    5. If sync=always: fsync.If fsync fails, switch to read-only mode and fail the write.
    6. Update KeyDir and the byte counters.
    7. Release the lock and reply OK.
    • Why one Write call. The file is opened with O_APPEND, so the kernel places each write at the current end of the file. One call per record means a record is never interleaved with another, and the only possible damage is a short tail.
    • Why truncate after a failed write. A half-written record in the middle of the file would make recovery stop there and cut off every good record written after it. Truncating keeps the file clean, so later writes stay readable.
    • Why read-only when truncate or fsync fails. At that point we no longer know what is on disk, and writing more could make it worse. Reads keep working. A restart runs recovery and finds out the truth.
    • Why KeyDir is updated after the write, not before. A reader can only find a record that is completely written. No GET can ever see half a value.
    • Why the KeyDir update is under the same lock as the write. Step through the bug below.
    The lost update: two clients write the same key at once

    GET, step by step

    1. Look the key up in KeyDir under a read lock.Missing → ErrKeyNotFound, with no disk access at all.
    2. Compute the record's offset and size, and read the whole record with one pread.
    3. Decode: check the CRC and compare the stored key.Mismatch → ErrCorrupt. Never return data that failed the check.
    4. Copy the value out and return it.The caller owns the returned slice and may change it.
    5. If the file vanished in between, go back to step 1.Compaction may delete the old file between steps 1 and 2. The store reports ErrSegmentNotFound, and by then KeyDir already points at the new file. At most three tries.

    pread means "positional read": read N bytes at offset X without moving a shared file position. Many goroutines can pread the same file at the same time without disturbing each other. In Go, os.File.ReadAt uses pread on Unix, and TinyCask's vfs.File exposes it through the io.ReaderAt interface. GET never takes the writer lock, so reads do not wait for writes.

    DELETE

    Under the writer lock: if the key is absent, return ErrKeyNotFound and write nothing. Otherwise append a tombstone, a record of type 2 with no value, and remove the key from KeyDir.

    Why this way

    "Why write a tombstone at all? Just remove the key from KeyDir."

    KeyDir is lost on every restart and rebuilt from the files. The old PUT is still in the files. Without a tombstone after it, recovery would bring the key back on every restart.

    07§5.4 Open (recovery)

    Crash recovery

    Recovery runs every time the engine opens. It turns the files back into a KeyDir.

    1. Create the directory if needed and take the LOCK.Already held by another process → ErrLocked.
    2. Clean up.Delete every *.tmp (an unfinished compaction). If a compact_M.data exists, delete every data file with ID < M. fsync the directory.
    3. Replay every file in ID order, each from offset 0.PUT → set KeyDir[key]. Tombstone → remove the key. Later records overwrite earlier ones, so the newest version wins.
    4. If a record fails to decode:in the file with the highest ID → truncate there, fsync, log a warning, continue (a torn tail). In any other file → stop, and Open fails with ErrCorrupt naming the file and offset.
    5. Create a new active segment with ID max + 1 and fsync the directory.
    6. Start the background goroutines.

    Why only the newest file may have a torn tail

    Writes only ever go to the end of the active file, and the active file always has the highest ID. Older files were fsynced when they were sealed and are never written again. If one of them is damaged, that is not an interrupted write. Data the client was told is safe is broken: bit rot, a disk fault, someone edited the file. Truncating would silently delete acknowledged data. Skipping is not possible either: the length fields of a damaged header cannot be trusted, so nobody knows where the next record starts. So the database stops and reports exactly where the damage is. This behaviour is called fail-stop: better to refuse to run than to run with silently wrong data.

    Why deleting the damaged key doesn't help

    Suppose a record in an old file is damaged, and you then DELETE (or overwrite) its key. The database still refuses to open. That is intended.

    • DELETE removes nothing. It appends a tombstone to the active file. The damaged bytes stay exactly where they were. Recovery reads every file from offset 0, so it meets the damage before it ever reaches the tombstone.
    • Recovery cannot find the next record. The damaged header's length fields cannot be trusted, so recovery does not know where the bad record ends. Every record after it in that file becomes unreadable, including live keys that nobody touched.
    • It cannot prove which key the record belongs to. The flipped bit may be in the key itself. "This was city, and city was deleted later" cannot be concluded from a record that failed its checksum.
    • Compaction cannot clean it up. The compactor reads the same files with the same decoder. It hits the bad record, deletes its .tmp and gives up (§5.5, failure handling). The damage stays until a person acts.

    The way out is a human decision: restore the file from a backup (the simulator's Undo bit rot button), or knowingly accept the loss, for example by moving the file out of the data directory. The engine never makes that choice on its own. ARCHITECTURE §14 lists "no salvage mode" as a known limitation.

    The simulator draws each damaged record with clear edges because it stores records as objects. The real engine only sees bytes, which is why the second point decides the matter.

    Why this way

    "The damaged record belongs to a key that was deleted later. Why not open anyway?"

    Because the engine cannot know that safely: it cannot trust the damaged key bytes, and it cannot find where the next record starts, so live data after the damage is at stake too. Throwing away acknowledged data is a decision for a person, not for a database at startup. TinyCask stops, names the exact file and offset, and leaves the choice to the operator.

    The other rules

    • Why replay in (file ID, offset) order. That is exactly the order in which the writes happened, so replaying it rebuilds exactly the state before the crash.
    • Why always a new active file. The old active file may just have been truncated. A fresh file is simple, and no code ever appends to a file from a previous run.
    • Cost. Startup time grows with the total size of the data, because every record is read. Accepted for v1.
    • Durability window. With sync=interval, a power cut can also lose up to a second of acknowledged writes. That is the durability policy (chapter 10), not a recovery flaw.
    Why this way

    "Isn't truncating dangerous? You delete data."

    Only the record that failed the check, at the very end of the newest file. That record's PUT never returned OK: the client is told OK only after the write fully succeeded. Truncating removes a write that never happened from the client's point of view.

    08§5.5 Compaction

    Compaction

    Every overwrite and every delete leaves garbage behind. Compaction copies only the live records into a new file and deletes the old files, while clients keep reading and writing.

    1. Seal and reserve.Seal the active file A, reserve ID M = A + 1 for the output, create the new active file A + 2. Inputs = every sealed file, all with ID < M. Microseconds; then the lock is released.
    2. Copy live records into compact_M.tmp.Scan the inputs. A PUT record is live only if KeyDir points at exactly this record: same file ID and same offset. Comparing values is not enough, two versions may hold the same value. Each copied key is remembered in a pending list.
    3. fsync the .tmp, rename it to compact_M.data, fsync the directory.From this moment the output is official on disk.
    4. Register the output in the segment set,so GET can read from it.
    5. Swap KeyDir entries in batches of at most 1024 keys.UpdateIf(key, entry.FileID < M, newEntry). Keys changed during the merge are left alone.
    6. Drop the inputs from the segment set, delete the files, fsync the directory.

    The simulator shows steps 3 and 4 as one step, so it counts five.

    The conditional swap

    What happened to the key during the mergeKeyDir entry at swap timeSwap?Why that is right
    NothingPoints into an input (ID < M)YesThe copy in M is the same record
    Overwritten by a new PUTPoints into a newer file (ID > M)NoThe newer value must win
    DeletedMissingNoThe tombstone sits in a file newer than M, so it also wins after a restart
    Deleted, then written againID > MNoSame as overwritten
    Why compaction must merge all old files: the resurrected key

    Why each rule is there

    • Why fsync before the rename. Right after the rename, step 6 deletes the inputs. If the output's bytes were still only in the page cache when the power failed, there would be a partial output and no old files: data loss. So the output must be durable before it becomes official.
    • Why rename is the "commit". rename() replaces a name atomically: anyone looking, recovery included, sees either the .tmp or the .data, never something in between. Before the rename, recovery deletes the unfinished .tmp. After it, recovery deletes the superseded inputs. There is no moment at which no valid copy exists.
    • Why the writer lock at the start. Sealing the active file and reserving M must happen together, so that no write lands in a file that is about to become an input, and every later write gets an ID above M.
    • Why batches of 1024. GET needs KeyDir's read lock. One write lock across a million updates would block all reads for tens of milliseconds and break the design doc's 5 ms rule. Short batches let reads slip in between.
    • When it runs. A background check every 10 s starts it when the garbage ratio is at least 0.5 and the data is at least 16 MiB. The COMPACT command starts it right away. Only one runs at a time (single-flight); a second request gets ErrCompactionRunning.
    • If it fails. Any error before the rename deletes the .tmp. Nothing else changes, and the engine stays writable.
    Why this way

    "Does compaction stop clients?"

    Only for very short moments: sealing and reserving the ID under the writer lock (microseconds), and each KeyDir batch (well under a millisecond each). Copying, the slow part, runs with no lock held.

    09§6 Concurrency model

    Locks and goroutines

    A goroutine is a lightweight thread managed by the Go runtime. TinyCask runs one per client connection, so many PUTs and GETs happen at the same time. Shared data needs protection: if two goroutines write a Go map at the same time, the runtime stops the program with fatal error: concurrent map writes; if two goroutines append to a file without coordination, the order of records is unpredictable.

    LockTypeProtectsHeld during disk I/O?
    Writer locksync.Mutex in engineThe append and its KeyDir update, rolls, switching to read-onlyYes, for the append itself
    KeyDir locksync.RWMutex in indexThe mapNever
    Store locksync.RWMutex in storageThe set of open files (ID → file)Read lock: yes, during pread. Write lock: only to change the set

    A mutex (mutual exclusion lock) lets one goroutine in at a time. A read-write mutex lets many readers in at once (RLock) or one writer alone (Lock). KeyDir uses the read-write kind because GETs vastly outnumber writes.

    Lock order

    writer lock→KeyDir lock→Store lock

    A goroutine may take these locks only in this order, never backwards. The reason is deadlock:

    The other rules

    • No disk I/O while holding the KeyDir lock. Disk operations take microseconds to milliseconds. Every GET needs this lock, so holding it during I/O would make all reads wait for the disk.
    • fsync outside the writer lock (sync=interval). fsync can take milliseconds. The background goroutine takes a reference to the active file under the lock, releases it, then calls fsync, so writers are not stalled.
    • Close a file only after removing it from the Store. Removal needs the Store's write lock, which waits until every reader holding the read lock has finished its pread. After removal no new reader can find the file, so closing it is safe.
    • Every goroutine has an owner. The accept loop, one goroutine per connection, the fsync ticker, the compaction ticker: each is tied to a context.Context for cancellation and a sync.WaitGroup to wait for it. Close cancels and waits. A goroutine nobody stops is a leak, and it might write to a file that is already closed.
    • Flags and counters use sync/atomic. closed, readOnly, "compaction running", liveBytes, diskBytes: single values read often, changed rarely.

    Data race vs race condition

    A data race is two goroutines touching the same memory at the same time without synchronization, where at least one writes. go test -race finds these. A race condition is a wrong result caused by timing, even when every access is properly locked. The lost-update bug from chapter 6 (two locks) is a race condition with no data race: the race detector would stay silent. That is why the project also has invariant checks and a model test.

    Why this way

    "Why not one big lock around everything? Simpler."

    Then every GET would wait behind every disk write and every fsync, and reads could never run in parallel. With the read-write KeyDir lock and lock-free pread, any number of GETs run at the same time, and writers block readers only for the instant of a map update.

    10§7 Durability

    Durability and fsync

    Durability is the promise that data the client was told is saved stays saved. To understand it you need the layers your bytes pass through:

    Your program's memory

    A []byte in the Go heap, or in a bufio.Writer buffer.

    lost on kill -9lost on power cut
    write() system call: returns as soon as the kernel has copied the bytes

    Kernel page cache

    RAM owned by the operating system. The kernel writes it to disk later, on its own schedule.

    survives kill -9lost on power cut
    fsync(): waits until the device confirms the data is stored

    The disk (SSD or HDD)

    fsync also asks the drive to flush its own small cache.

    survives kill -9survives power cut

    This is why TinyCask writes every record with one unbuffered Write call: the moment the client gets OK, the record is at least in the page cache and survives a crash of the process. If records were collected in a Go buffer first, an acknowledged write could die with the process.

    fsync is slow, from tens of microseconds to many milliseconds. On macOS, Go's File.Sync uses F_FULLFSYNC, which also empties the drive's cache. That is the honest kind of fsync, and on a laptop it limits you to a few hundred or a few thousand per second. That is why sync=always cannot reach the design doc's 12,000 writes per second.

    sync modeWhen fsync happensAfter kill -9After a power cut
    alwaysAfter every write, before OKNothing lostNothing lost
    interval (default, 1 s)A background timerNothing lostUp to about 1 s of writes
    neverRoll, compaction, CloseNothing lostWhatever the OS had not flushed

    RPO (recovery point objective) is how much acknowledged data you may lose. The design doc: RPO = 0 for a process crash in every mode; RPO = 0 for a power cut only with sync=always. Redis makes the same default choice as TinyCask (appendfsync everysec).

    Why the directory is fsynced too

    A file's name lives in its directory, and a directory is a file too. Creating, renaming or deleting a file changes the directory. Until the directory itself is fsynced, a power cut can forget that a new file exists or bring back a deleted one. So the engine calls SyncDir after every create, rename and delete.

    Why a failed fsync is never retried

    In 2018 PostgreSQL developers found that on Linux, after fsync reports an error, the kernel may drop the unwritten pages and mark them clean. A second fsync then reports success although the data never reached the disk. This became known as "fsyncgate". Retrying is therefore a lie. PostgreSQL's fix was to stop instead of retrying. TinyCask stops writing (read-only mode) and keeps serving reads.

    Why this way

    "Why is the default allowed to lose a second of data?"

    It is a speed-for-safety trade made explicitly and configurable. fsync on every write would cap throughput at what the drive can flush. Most workloads accept losing a second on a power cut; those that cannot set sync=always. A process crash loses nothing in any mode.

    11§8 Error handling

    Errors

    In Go an error is a normal return value, not an exception. A function that can fail returns error as its last result, and the caller decides what to do. TinyCask's rules:

    ErrorMeaning
    ErrKeyNotFoundGET or DELETE of a key that does not exist
    ErrInvalidKey, ErrKeyTooLarge, ErrValueTooLargeThe request breaks the size limits
    ErrNoSpaceThe disk is full; the write was rolled back
    ErrReadOnlyAn earlier fsync or truncate failed; writes are refused until restart
    ErrClosedThe engine was closed
    ErrCorruptA record failed its checks
    ErrLockedAnother process holds the directory
    ErrCompactionRunningA compaction is already in progress
    • Sentinel errors are package-level values like var ErrKeyNotFound = errors.New("engine: key not found"). Callers compare with errors.Is(err, engine.ErrKeyNotFound).
    • Wrapping adds context without losing the original: fmt.Errorf("open %s: %w", name, err). The message grows ("open seg_0000000003.data: write: no space left on device") and errors.Is still finds the original inside.
    • Each layer has its own errors (vfs.ErrNoSpace, storage.ErrCorrupt, storage.ErrSegmentNotFound), and the engine translates them at its boundary. The server only needs to know the engine's errors.
    • Never compare error text. Messages change and wrapping changes them; errors.Is checks identity through the whole chain.
    • No panic on bad input. Bytes from disk and from the network are input. A panic on bad input turns one corrupt file or one hostile client into a dead server. panic is only for "this cannot happen" programmer bugs.
    • Log once, at the place that handles the error, not at every level it passes through.
    • Read-only is one-way. Within one process the engine never becomes writable again. Only a restart, which runs recovery, can establish what is really on disk.
    12§9 Wire protocol

    The network protocol

    Clients talk to TinyCask over TCP, port 6380, using a subset of RESP2, the protocol Redis uses. That is why the standard redis-cli and redis-benchmark tools work as TinyCask's client and load generator without writing either.

    *3\r\n$3\r\nSET\r\n$4\r\nuser\r\n$4\r\ndata\r\n
    *3 an array of 3 elements$4 a bulk string of 4 bytesthe bytes themselves\r\n line end

    Because every bulk string starts with its length, the value can contain any bytes: spaces, line breaks, zero bytes. The parser reads exactly that many. This property is called binary-safe. For typing by hand in nc or telnet there is also the inline form, SET user data\r\n, which cannot contain spaces inside a key or value.

    CommandReplyRESP type
    PING+PONGsimple string
    SET k v / PUT k v+OKsimple string
    GET k$4\r\ndata, or $-1 if absentbulk string / nil
    DEL k / DELETE k:1 deleted, :0 absentinteger
    COMPACT+OK when the merge finishessimple string
    INFOkeys:… linesbulk string
    any failure-ERR no_space …error
    • Limits before allocation. A client could send $999999999999. The parser checks every length against the limits (line ≤ 64 KiB, ≤ 8 elements, bulk ≤ the max value size) before it allocates or reads anything. FuzzParseFrame tests this with millions of random inputs.
    • Pipelining. A client may send 100 commands without waiting for answers. The server reads them one by one, writes replies into a buffer, and sends the buffer when no more input is waiting: one network round trip instead of 100.
    • Connections. One goroutine per connection. At most 1024 connections; extra ones are closed at once. An idle connection is closed after 5 minutes; a reply that cannot be written in 10 seconds closes the connection.
    • Shutdown. On Ctrl+C (SIGINT) or SIGTERM: stop accepting, let running commands finish for up to 5 s, then close the engine. This is a graceful shutdown.
    • Errors on the wire. Engine errors map to short codes (no_space, read_only, invalid_argument, corrupt, busy). Anything unexpected becomes internal; details go to the log, never to the client.
    Why this way

    "Why not HTTP with JSON?"

    More parsing, no binary values without base64, and we would have to write our own client and benchmark tool. RESP is tiny to parse, binary-safe, and comes with mature tools. The design doc's text form <COMMAND> <KEY> [<VALUE>]\r\n still works as RESP's inline form.

    13§2, §10, §12

    Packages and layers

    A Go package is a directory of .go files compiled together. Packages under internal/ can only be imported by code in the same module, so nothing outside TinyCask can depend on them and you can change them freely.

    • Why one direction only. Go refuses to compile import cycles. A one-way graph also means each layer can be tested alone: index without any disk, storage on a fake disk, the server with a fake engine.
    • Why vfs and index import nothing. They are the foundations. index is a pure data structure, so its concurrency tests are simple and fast.
    • Why the server sees so little. It only knows the engine's error values and stats, and talks to the store through a small interface it defines itself. Its tests use a fake store, with no disk involved.
    • Enforced, not hoped for. The linter rule depguard (inside golangci-lint) fails the build if code outside vfs imports os file functions or if non-test code imports simfs.

    The engine's public API

    Configuration

    Everything is a command-line flag: -addr :6380, -dir ./data, -sync interval, -sync-interval 1s, -max-segment-size 64MiB, -max-key-size 1KiB, -max-value-size 1MiB, -compact-ratio 0.5, -compact-min-bytes 16MiB, -compact-interval 10s (0 turns it off), -max-conns 1024.     14§11 VFS contract

    The fake disk: VFS and SimFS

    Every disk operation in TinyCask goes through two small interfaces, vfs.FS and vfs.File. VFS stands for virtual file system. In production they are implemented by OSFS, which uses real files. In tests, by SimFS: a file system that lives in memory and fails on command.

    type FS interface {
    Create(name string) (File, error)     // new file, fails if it exists
    Open(name string) (File, error)       // existing file
    Remove(name string) error
    Rename(oldName, newName string) error // atomic replace
    List(dir string) ([]string, error)    // sorted names
    MkdirAll(dir string) error
    SyncDir(dir string) error
    Lock(name string) (io.Closer, error)  // exclusive, ErrLocked if held
}

type File interface {
    io.Writer   // always appends
    io.ReaderAt // pread
    io.Closer
    Sync() error
    Truncate(size int64) error
    Size() (int64, error)
}

    Why bother? Crash bugs are about what happens when a write fails halfway or the power goes off at the worst possible moment. You cannot make a real disk do that on cue, reliably, 2,000 times in one test run. SimFS can, and it is deterministic: a failing test fails the same way every time, so you can debug it.

    The four faults

    1. Fail the Nth call of an operation with a chosen error. Example: the 3rd Sync fails.
    2. Tear a write at byte N, then crash. Part of a record reaches the "disk", then the process is dead.
    3. Disk quota. A write that does not fit stores what fits and returns ErrNoSpace.
    4. Lose unsynced bytes on restart. Every file is cut back to what was last fsynced: a power cut.

    After a simulated crash, every call returns ErrCrashed until Restart(), and old file handles stay dead, exactly like after a real process death. One documented simplification: creating, renaming and deleting files is durable at once in SimFS. The engine still calls SyncDir, but SimFS cannot detect a missing call.

    Keeping the fake honest

    A conformance suite is one set of tests run against both OSFS and SimFS. If SimFS behaved differently from a real disk in any way the suite checks, it would fail. Otherwise a test could pass on the fake and the bug would still exist on real disks.

    Every crash test follows the same shape: arm a fault, run until ErrCrashed, Restart(), reopen the engine, compare with the expected state, check the invariants.

    15§13 Testing architecture

    Testing strategy

    KindWhat it provesExample
    UnitOne piece works aloneEncode then decode returns the same record
    GoldenThe byte format never changes by accidentA committed file holds the exact bytes of a sample record
    ConformanceThe fake disk behaves like the real oneOne suite for OSFS and SimFS

    The model test

    A generator, started from a seed (a number that fixes the random sequence), produces random PUTs, DELETEs, GETs and COMPACTs. They run against TinyCask and against a plain Go map, the model. At a random moment the fake disk crashes; the engine restarts and is compared with the model. Every acknowledged write must be there; the interrupted one is either fully there or absent. If it ever fails, rerunning with the same seed reproduces the exact failure. This one test covers combinations nobody would think to write by hand. The simulator on this page was checked the same way.

    Invariants

    An invariant is a statement that must be true at all times. The design doc's two: the number of keys in KeyDir equals the number of keys whose last record in the log is not a tombstone; and every KeyDir entry points at a record whose CRC is valid. A test helper checks both after every reopen by scanning the files on its own, without trusting KeyDir.

    Fuzzing

    go test -fuzz feeds millions of mutated inputs into a function, guided by which code paths they reach, looking for panics. For the decoder and the parser the property is simple: never panic, never allocate absurdly, and decoding followed by encoding returns the same bytes. Any crashing input it finds is saved under testdata/fuzz/ and becomes a permanent regression test.

    Benchmarks and P99

    Throughput is operations per second. P99 latency is the time that 99% of requests beat; it shows the slow tail that an average hides. Timing assertions in tests are flaky on laptops and CI machines, so benchmarks report numbers and never fail a build. Results go into BENCHMARKS.md next to the design doc's targets, reported as measured.

    Coverage targets: over 85% overall, at least 90% for storage, engine and compactor, and every fault point exercised by at least one test.

    17Go primer

    Go idioms in the code

    Only the parts of Go TinyCask uses, each with the reason it matters here. The longer snippets were compiled and run with Go 1.27 while this guide was written.

    Modules, packages and exported names

    A module is the whole project, defined by go.mod (module github.com/…/TinyCask, go 1.27). A package is one directory. A name starting with a capital letter (Engine, Open) is exported, visible to other packages; a lowercase name (appendFrame) is private to its package. There is no public keyword: capitalisation is the rule.

    Structs, methods, pointer receivers

    type Engine struct {
    mu       sync.Mutex  // writer lock: guards the active file and the KeyDir update
    readOnly atomic.Bool
    wg       sync.WaitGroup
}

// Pointer receiver (*Engine): the method works on the shared Engine, not a copy.
func (e *Engine) Put(key, value []byte) error {
    frame := encode(key, value) // outside the lock
    e.mu.Lock()
    defer e.mu.Unlock()
    // append, then update KeyDir ...
    return nil
}

    Types that contain a mutex must always be used through a pointer. Copying a struct copies its mutex, including whether it is locked, and go vet warns about it (the "copylocks" check).

    Interfaces are satisfied implicitly

    type File interface {
    Write(p []byte) (int, error)
    Sync() error
}

type memFile struct{ data []byte }

func (m *memFile) Write(p []byte) (int, error) { m.data = append(m.data, p...); return len(p), nil }
func (m *memFile) Sync() error                 { return nil }

var _ File = (*memFile)(nil) // compile-time proof that *memFile is a File

    There is no implements keyword. Any type with the right methods is a File. That is how OSFS and SimFS both become a vfs.FS, and how the engine can run on either without knowing which. The last line is a common trick: it fails to compile if memFile ever stops matching the interface.

    Errors: sentinels, wrapping, Is, Join

    var ErrKeyNotFound = errors.New("engine: key not found")

func lookup(key string) error {
    return fmt.Errorf("get %q: %w", key, ErrKeyNotFound) // %w wraps
}

err := lookup("user")
fmt.Println(err)                            // get "user": engine: key not found
fmt.Println(errors.Is(err, ErrKeyNotFound)) // true

// Two failures at once (a failed write, then a failed cleanup):
return errors.Join(writeErr, truncErr)

    %w keeps the original error inside the new one; %v would only copy its text and errors.Is would stop working. errors.As is the variant that extracts an error of a specific type.

    defer

    defer f() runs f when the surrounding function returns, whichever way it returns. It is the standard way to unlock a mutex or close a file. Two traps: a defer inside a loop only runs when the whole function ends, and a deferred Close() silently drops its error. For files that were written, check it:

    func writeAll(f vfs.File, b []byte) (err error) {
    defer func() {
        if cerr := f.Close(); cerr != nil && err == nil {
            err = cerr // report the Close error if nothing else failed
        }
    }()
    _, err = f.Write(b)
    return err
}

    Slices share memory

    buf := []byte("user")
m := map[string][]byte{}
m["k"] = buf      // stores the same underlying array, not a copy
buf[0] = 'X'
fmt.Println(string(m["k"])) // Xser  (the stored value changed!)

safe := bytes.Clone(buf)    // an independent copy

idx := map[string]int{}
idx[string(buf)] = 1        // string(buf) copies, so the map key is safe

    A slice is a small header pointing at an array. Assigning a slice copies the header, not the data. This is why the engine copies values it returns and never keeps the caller's slices, and why KeyDir uses map[string].

    Maps are not safe for concurrent use

    A Go map read and written by two goroutines at once crashes the program (or worse, corrupts silently under the race detector's radar). Every shared map needs a mutex; KeyDir's is a sync.RWMutex.

    Goroutines, channels, select, context, WaitGroup

    func (e *Engine) startSyncLoop(ctx context.Context, every time.Duration) {
    e.wg.Go(func() { // starts a goroutine and counts it in the WaitGroup
        t := time.NewTicker(every)
        defer t.Stop()
        for {
            select {
            case <-ctx.Done(): // Close cancelled the context
                return
            case <-t.C: // the ticker fired
                if err := e.syncActive(); err != nil {
                    e.log.Error("background sync failed", "err", err)
                }
            }
        }
    })
}

// In Close():
cancel()     // tell every background goroutine to stop
e.wg.Wait()  // and wait until they all have
    • go f() starts a goroutine. wg.Go(f) (Go 1.25+) does the same and registers it with the WaitGroup.
    • A channel passes values between goroutines; <-ch waits for one. select waits on several channels and runs the case that is ready first.
    • A context carries a cancellation signal. ctx.Done() is a channel that closes when someone calls cancel().
    • A WaitGroup counts running goroutines; Wait() blocks until the count is zero.

    sync and sync/atomic

    sync.Mutex: Lock/Unlock. sync.RWMutex: RLock/RUnlock for readers, Lock/Unlock for the writer. atomic.Bool and atomic.Int64 are single values that many goroutines can Load and Store safely without a mutex, which suits flags like readOnly and counters like liveBytes.

    io interfaces and bufio

    io.Writer (Write(p) (n, err)), io.ReaderAt (ReadAt(p, off) (n, err)) and io.Closer are tiny standard interfaces that vfs.File combines. bufio.Reader wraps a network connection so the RESP parser can read line by line; io.ReadFull reads exactly N bytes for a bulk string or fails. Remember: ReadAt returns io.EOF when fewer bytes exist than asked for, which is how a scanner notices a short record.

    encoding/binary and hash/crc32

    buf := make([]byte, 21+len(key)+len(value))
binary.LittleEndian.PutUint64(buf[4:12], uint64(ts))
buf[12] = 1 // PUT
binary.LittleEndian.PutUint32(buf[13:17], uint32(len(key)))
