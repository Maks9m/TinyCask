# Design Document: TinyCask (In-Memory KeyDir + Append-Only Log Store)

**Мова реалізації:** Go  
**Тип проєкту:** Локальна Key-Value база даних  

---

## 1. Мета та обмеження (Goals & Non-Goals)

### 1.1. Цілі (Goals)
* **Висока швидкість виконання:** Забезпечити затримку $O(1)$ для запису (append-only) та $O(1)$ для читання (прямий системний виклик `pread` за офсетом із диска).
* **Гарантія збереження даних (Crash-Safety):** Захистити існуючі дані від пошкодження при раптовому вимкненні живлення або аварійному завершенні процесу (`kill -9`, `Ctrl+C`) завдяки append-only архітектурі логу.
* **Детермінована відмовостійкість (Fault Injection):** Побудувати систему хаос-тестування на основі віртуалізованого середовища (VFS), яка дозволяє імітувати системні збої (брак місця на диску, обрив запису) та перевіряти цілісність індексу після відновлення.
* **Контроль дискового простору:** Реалізувати фонове злиття логів (Compaction) для видалення застарілих версій ключів та маркерів видалення (Tombstones).

### 1.2. Поза межами проєкту (Non-Goals)
* Розподілені мережеві консенсуси (Raft/Paxos), реплікація або шардинг (система є суворо локальною).
* Транзакційні гарантії (ACID) для операцій над кількома ключами одночасно.
* Підтримка обсягу ключів, що перевищує розмір RAM (KeyDir повністю утримується в оперативній пам'яті).

## 2. Архітектура системи (System Architecture)

Система складається з 5 ізольованих шарів, що взаємодіють між собою через Go-інтерфейси:

```text
+---------------------------------------------------+
|                 TCP Network Server                |
|        (Connection Pool & Custom Protocol)        |
+---------------------------------------------------+
                          |
                          v
+---------------------------------------------------+
|               Engine (Façade API)                 |
|            PUT()  |  GET()  |  DELETE()           |
+---------------------------------------------------+
              |                           |
              v                           v
+---------------------------+ +---------------------+
|   KeyDir (In-Memory)      | | Storage Engine(Disk)|
|   • Hash Map Index        | | • Active Segment(W) |
|   • sync.RWMutex          | | • Inactive Seg.(R)  |
+---------------------------+ | • Compactor (Merge) |
                              +---------------------+
                                         |
                                         v
                              +---------------------+
                              | VFS(Abstraction L.) |
                              | OS FS / SimulatorFS |
                              +---------------------+

```

### 2.1. Специфікація модулів

* **TCP Network Server & Protocol Parser (`pkg/server`):**
* **Модель паралельності:** Goroutine-per-Connection. При надходженні підключення створюється окрема горутина.
* Парсить текстовий протокол (`<COMMAND> <KEY> [<VALUE>]\r\n`) через буферизований читач (`bufio.Reader`), захищаючи пам'ять від OOM при аномальних запитах.


* **KeyDir (In-Memory Index, `pkg/index`):**
* Потокобезпечна хеш-таблиця (`sync.RWMutex`), яка зберігає метадані розташування ключів у лог-файлах.



```go
type KeyDir struct {
    mu    sync.RWMutex
    index map[string]CommandIndex
}

type CommandIndex struct {
    FileID      uint32 // Ідентифікатор сегментного файлу
    ValueSize   uint32 // Довжина значення в байтах
    ValueOffset int64  // Абсолютний офсет початку Value у файлі
    Timestamp   uint64 // Час створення/оновлення запису
}

```

* **Storage Engine (`pkg/storage`):**
* **Active Segment:** Єдиний файл, відкритий у режимі Append-Only (`O_APPEND | O_WRONLY`) для запису нових даних.
* **Immutable Segments:** Закриті файли даних, доступні тільки для читання.


* **Compaction Engine (`pkg/compactor`):**
* Фоновий процес, який зливає застарілі сегменти, відфільтровує видалені ключі й вивільняє дисковий простір.


* **Virtual File System (VFS Layer, `pkg/vfs`):**
* Абстракція над дисковими операціями для можливості підключення симулятора аварій.



### 2.2. Формат зберігання даних (Binary Format)

Усі операції модифікації (PUT, DELETE) створюють бінарний кадр (Frame) у кінці Active-файлу. Дані ніколи не перезаписуються "на місці".

```text
+------------------+---------------+---------------+---------------+---------------+---------------+
|    CRC32 (4B)    | Timestamp(8B) | Key Size(4B)  | Val Size(4B)  |   Key (KB)    |  Value (VB)   |
+------------------+---------------+---------------+---------------+---------------+---------------+
|<--------------------- Fixed Header (20 Bytes) ------------------->|<---- Dynamic Payload ------>|

```

**Поля кадру:**

* **CRC32 (4 bytes)** — контрольна сума для блоку `[Timestamp + KeySize + ValSize + Key + Value]`.
* **Timestamp (8 bytes)** — nanoseconds Unix Epoch.
* **Key Size (4 bytes)** — довжина ключа $K$.
* **Value Size (4 bytes)** — довжина значення $V$ ($0$ для Tombstone).
* **Key** — $K$ байтів ключа.
* **Value** — $V$ байтів значення.

> **Маркер видалення (Tombstone):** При виклику `DELETE` створюється кадр, у якому `Value Size = 0`.

### 2.3. Алгоритми виконання операцій

#### Операція `PUT(Key, Value)`

1. Engine обчислює CRC32 та збирає бінарний Frame у пам'яті.
2. Frame додається в кінець Active Segment (операція захищена `sync.Mutex`).
3. Після успішного I/O оновлюється запис у KeyDir (`FileID`, `ValueOffset`, `ValueSize`, `Timestamp`).
4. Клієнту повертається відповідь OK.

#### Операція `GET(Key)`

1. Пошук запису в KeyDir під `RLock()`. Якщо не знайдено — повертається `ErrKeyNotFound`.
2. Отримуються `FileID`, `ValueOffset`, `ValueSize`.
3. Виконується системний виклик `pread(FileID, ValueOffset, ValueSize)`.
4. Зчитується Header, розраховується CRC32. Якщо цілісність підтверджено — повертається `Value`.

#### Операція `DELETE(Key)`

1. У лог пишеться кадр-Tombstone (`Value Size = 0`).
2. Ключ атомарно видаляється з KeyDir.

### 2.4. Алгоритм відновлення (Crash Recovery)

При запуску системи індекс KeyDir відбудовується з дискових логів за наступним алгоритмом:

```text
[Старт] --> [Послідовне сотування сегментів за ID]
                    |
                    v
       [Читання файлу від Offset 0 до кінця]
                    |
                    +--> [Перевірка CRC32 кадру]
                    |            |
                    |            +-- [CRC OK] -------> [Оновлення KeyDir]
                    |            |
                    |            +-- [CRC BAD / Partial Write]
                    |                                  |
                    v                                  v
[Створення нового Active Segment] <--- [Обрізання битого хвоста файлу]

```

### 2.5. Фонове злиття (Compaction) та усунення гонок з PUT/DELETE

Оскільки `PUT` та `DELETE` завжди пишуть виключно в Active Segment ($S_{active}$), фоновий процес Compactor працює за алгоритмом умовного оновлення індексу (Conditional Index Update), що виключає втрату нових даних:

1. **Ізоляція:** Compactor фіксує список тільки закритих Immutable-сегментів ($S_1, S_2, \dots, S_k$) на момент старту і створює новий файл `compact_X.tmp`. Active Segment ($S_{active}$) при цьому залишається повністю відкритим для паралельних записів клієнтів.
2. **Перенесення даних:** Compactor вичитає старі сегменти й копіює в `compact_X.tmp` тільки ті ключі, які є актуальними за версією KeyDir.
3. **Умовне оновлення KeyDir (Conditional Update):** Після закінчення запису Compactor бере короткотривале блокування `KeyDir.Lock()` і для кожного перенесеного ключа $K$ виконує перевірку:
* Якщо `KeyDir[K].FileID` все ще вказує на один зі старих сегментів ($S_1 \dots S_k$) — координати ключа в KeyDir оновлюються на новий файл `compact_X.data`.
* Якщо `KeyDir[K].FileID` вказує на $S_{active}$ (це означає, що під час злиття клієнт виконав новий `PUT` або `DELETE` для цього ключа) — перенесення для цього ключа скасовується, а запис у KeyDir залишається недоторканим.


4. **Очищення:** Старі файли $S_1, \dots, S_k$ атомарно видаляються з диска.

### 2.6. Модель паралельності та синхронізації

| Ресурс / Компонент | Механізм захисту | Опис |
| --- | --- | --- |
| **KeyDir Index** | `sync.RWMutex` | Паралельні читачі (`GET`) беруть `RLock()`, записники (`PUT`/`DELETE`) беруть `Lock()`. |
| **Active Segment** | `sync.Mutex` | Синхронізація послідовного додавання записів (Append) від багатьох паралельних TCP-горутин. |
| **Immutable Segments** | Stateless `pread` | Не потребує блокувань на рівні Go-коду; kernel гарантує безпечне читання з файлового офсету. |
| **Compactor vs KeyDir** | Atomic Pointer / Lock | Під час заміни сегментів Compactor бере короткий `KeyDir.Lock()`, щоб оновити `FileID` та `ValueOffset` для перенесених ключів. |

## 3. Стратегія та специфікація тестування (Testing Strategy)

### 3.1. Класифікація тестів (Test Taxonomy)

* **Unit Tests (White-Box):** Ізольоване тестування бінарного кодека, розрахунку CRC32 та потокобезпеки хеш-карти KeyDir.
* **Integration Tests (Gray-Box):** Перевірка взаємодії дискового двигуна, індексу KeyDir та фонового Compactor.
* **Fault Injection & Chaos Tests (Simulation):** Детерміноване тестування стійкості до відмов за допомогою симулятора файлової системи (SimulatorFS).
* **Fuzzing & Property-Based Tests (Black-Box):** Перевірка інваріантів та пошук граничних випадків парсера за допомогою `go test -fuzz`.

### 3.2. Матриця покриття модулів (Test Coverage Matrix)

| Модуль / Компонент | Рівень тесту | Метод тестування | Тестові сценарії (Test Cases) |
| --- | --- | --- | --- |
| **CRC32 & Binary Codec** | Unit | White-Box | • Серіалізація/десеріалізація заголовка<br><br>• Виявлення спотворення байтів (bit rot)<br><br>• Крайові випадки ($V=0$, порожні ключі) |
| **KeyDir Index** | Unit | White-Box | • Concurrent Map Read/Write під навантаженням (`go test -race`)<br><br>• Обробка неіснуючих ключів (KeyNotFound) |
| **TCP Protocol Parser** | Unit / Fuzzing | Black-Box / Fuzz | • Парсинг неповних/обірваних фреймів<br><br>• Некоректні команди та синтаксичні помилки<br><br>• Fuzzing випадкових бінарних послідовностей |
| **Active Segment & KeyDir** | Integration | Gray-Box | • `PUT` атомарно оновлює лог і KeyDir<br><br>• `DELETE` додає Tombstone і видаляє ключ з KeyDir |
| **Compactor Engine** | Integration | Gray-Box | • Видалення застарілих версій ключів при злитті<br><br>• Збереження тільки актуальних даних<br><br>• Атомарність операції Rename |
| **Storage Recovery** | Fault Injection | Chaos / Simulation | • Partial Write Crash: Завершення роботи під час запису кадру<br><br>• Corrupted Log: Пропуск битого запису при старті<br><br>• Відновлення KeyDir з кількох сегментів |
| **Virtual Disk Simulator** | Fault Injection | Chaos / Simulation | • Disk Full (`ErrNoSpace`): Граційна відмова при переповненні<br><br>• IO Timeout / Write Error: Відкот операції в пам'яті |

### 3.3. Деталізація сценаріїв Хаос-тестування (Fault Injection Specs)

Хаос-тести виконуються в пам'яті через абстракцію SimulatorFS, що робить їх детермінованими та миттєвими.

#### Сценарій 1: Partial Write / Partial Record Crash (Обрив запису при аварії)

* **Передумова:** Клієнт відправляє `PUT("user", "data")`. Симулятор диска перериває операцію запису `Write()` після того, як записав заголовок (Header), але до повного збереження Body.
* **Дія:** Процес перезапускається (Reboot). Викликається алгоритм відновлення індексу `Recover()`.
* **Очікуваний результат:**
* Двигун зчитує неповний запис, обчислює CRC32 і виявляє розбіжність.
* Неповний запис ігнорується (обрізається хвіст файлу).
* Індекс KeyDir відновлюється до останього цілісного стану.
* База продовжує коректну роботу без пошкодження попередніх даних.



#### Сценарій 2: Interrupted Compaction (Аварія під час прибирання сміття)

* **Передумова:** Процес Compactor зчитує 3 сегменти й пише відфільтровані дані у тимчасовий файл `compact_102.tmp`.
* **Дія:** Симулятор викликає `Kill()` під час виконання запису у `.tmp` файл (до моменту атомарного Rename).
* **Очікуваний результат:**
* Початкові 3 сегменти залишаються недоторканими й активними.
* При наступному старті база виявляє неоформлений `compact_102.tmp` і видаляє його.
* Жоден актуальний ключ не втрачено.



#### Сценарій 3: Симуляція відсутності вільного місця (`ErrNoSpace`)

* **Передумова:** Налаштовано ліміт симулятора диска у 1 МБ. База заповнена на 999 КБ.
* **Дія:** Відправляється `PUT` розміром 10 КБ.
* **Очікуваний результат:**
* Метод `Write()` повертає POSIX `ErrNoSpace`.
* Запис у KeyDir не додається (операція атомарно відкочується).
* Клієнту повертається чітка помилка `ERR no_space`.



### 3.4. Перевірка інваріантів та Фаззінг (Invariants & Fuzzing)

#### Інваріанти цілісності (Property-Based Verification)

Для будь-якого стану логу після відновлення повинні виконуватися математичні інваріанти цілісності:

$$\text{Count}(\text{KeyDir}) = \text{Count}(\text{Unique Non-Deleted Keys in Log})$$

$$\forall k \in \text{KeyDir}: \text{CRC32}(\text{pread}(k.\text{FileID}, k.\text{ValueOffset}, k.\text{ValueSize})) == \text{Valid}$$

*Пояснення формули:* Кількість елементів в in-memory індексі KeyDir строго дорівнює кількості унікальних ключів у дискових сегментах, останнім записаним станом яких не є Tombstone (`Value Size = 0`).

#### Fuzz-тестування бінарного парсера

За допомогою Go Fuzzing (`go test -fuzz=FuzzParseFrame`) генеруються мільйони псевдовипадкових байтових послідовностей на вхід TCP-парсеру.

* **Мета:** Переконатися, що парсер ніколи не спричиняє `panic` або `out-of-memory` за будь-яких некоректних даних у мережі.

### 3.5. Метрики та інструменти тестування

* **Тестовий фреймворк:** Стандартний `testing` + `github.com/stretchr/testify` (для `assert`/`require`).
* **Детектор гонок (Race Detection):** Усі інтеграційні та юніт-тести обов'язково проходять перевірку прапорцем `go test -race ./...`.
* **Покриття коду (Code Coverage):**
* Загальний цільовий показник: $> 85\%$.
* Покриття модулів Storage Engine та Recovery: $100\%$.

## 4. Нефункціональні вимоги (Non-Functional Requirements)

### 4.1. Продуктивність, Затримки та Бенчмаркінг (Performance Specs)

Для оцінки деградації продуктивності під час фонового Compaction та на змішаному навантаженні встановлюються наступні цільові метрики:

| Сценарій навантаження | Метрика P99 Latency | Метрика Throughput | Метод вимірювання / Верифікація |
| --- | --- | --- | --- |
| **GET Only (100% Читання)** | $\le 1\text{ ms}$ | $\ge 20,000\text{ ops/sec}$ | Паралельні `pread` без блокування Active Segment |
| **PUT Only (100% Запис)** | $\le 4\text{ ms}$ | $\ge 12,000\text{ ops/sec}$ | Запис з буферизацією дискового I/O |
| **Mixed Workload (80% GET, 15% PUT, 5% DELETE)** | $\le 3\text{ ms}$ | $\ge 15,000\text{ ops/sec}$ | Симуляція реального профілю навантаження багатьох клієнтів |
| **Mixed Workload під час активного Compaction** | $\le 5\text{ ms}$ (деградація $\le 60\%$) | $\ge 10,000\text{ ops/sec}$ | Вимірювання P99 під час активного злиття 1 GB файлів на диску |

#### Порівняльний бенчмаркінг (Compaction vs Baseline)

Під час автоматичного тестування (`go test -bench`) проводиться обов'язковий тест порівняння продуктивності:

* **Baseline Test:** Вимірювання затримки P99 та пропускної здатності при вимкненому Compacting.
* **Stress Compaction Test:** Примусовий запуск фонового Compactor під підключеним змішаним навантаженням.
* **Критерій успішності (Pass Condition):** Деградація затримки P99 для GET операцій під час роботи Compactor не повинна перевищувати $5\text{ ms}$ (допускається зниження Throughput не більше ніж на $35\text{–}40\%$).

### 4.2. Надійність та Збереження даних (Reliability & Durability)

* **Recovery Point Objective (RPO = 0):** Жоден підтверджений клієнту PUT-запит не повинен бути втрачений при звичайному закритті процесу або аварійному `Ctrl+C`.
* **Zero Corruption Propagation:** При пошкодженні байтів у кінці логу (Partial Write) система повинна атомарно відкотити нецілісний запис, ізолювати помилку та продовжити роботу без падіння процесу (`panic`).
* **Compaction Safety:** Фонове злиття файлів не повинно блокувати операції читання (GET) більше ніж на $5\text{ ms}$ у момент атомарного перейменування файлу `rename()`.

### 4.3. Використання ресурсів (Resource Efficiency)

#### Оверхед пам'яті для KeyDir (Memory Footprint)

Розмір індексу в RAM обчислюється за формулою:

$$\text{RAMUsage} \approx N \times (\text{Len}(\text{Key}) + 48\text{ bytes})$$

де $N$ — кількість унікальних ключів. База повинна утримувати $1,000,000$ ключів у межах $\sim 100\text{--}150\text{ МБ RAM}$.

* **Дисковий оверхед (Disk Amplification):** Фоновий Compactor запускається при досягненні співвідношення застарілих даних (Tombstones + старі версії) $\le 50\%$ від загального обсягу дискових сегментів.

### 4.4. Обмеження реалізації (Maintainability Constraints)

* **Обсяг коду (Code Budget):** Ядро системи не перевищує 2500–3000 LOC, що гарантує високу читабельність та простоту проведення коду-рев'ю.
* **Мінімальні зовнішні залежності (Zero-Dependency Policy):**
* Для ядра та VFS використовувати виключно стандартну бібліотеку Go (`os`, `sync`, `net`, `encoding/binary`).
* Зовнішні бібліотеки дозволені тільки для тестів (`github.com/stretchr/testify`).
