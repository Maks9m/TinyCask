# Design Document: TinyCask (In-Memory KeyDir + Append-Only Log Store)

**Мова реалізації:** Go  
**Тип проєкту:** Локальна Key-Value база даних  
**Версія документа:** 1.1 — уточнення затвердженої версії 1.0 без зміни архітектури (перелік змін — у розділі 5)

---

## 1. Мета та обмеження (Goals & Non-Goals)

### 1.1. Цілі (Goals)
* **Висока швидкість виконання:** Забезпечити затримку $O(1)$ для запису (append-only) та $O(1)$ для читання (один системний виклик `pread` за офсетом із диска).
* **Гарантія збереження даних (Crash-Safety):** Захистити існуючі дані від пошкодження при аварійному завершенні процесу (`kill -9`) або раптовому вимкненні живлення завдяки append-only архітектурі логу. `Ctrl+C` (SIGINT) та SIGTERM обробляються як штатне завершення (graceful shutdown), а не як аварія.
* **Детермінована відмовостійкість (Fault Injection):** Побудувати систему хаос-тестування на основі віртуалізованого середовища (VFS), яка дозволяє імітувати системні збої (брак місця на диску, обрив запису, втрату несинхронізованих даних) та перевіряти цілісність індексу після відновлення.
* **Контроль дискового простору:** Реалізувати фонове злиття логів (Compaction) для видалення застарілих версій ключів та маркерів видалення (Tombstones).

### 1.2. Поза межами проєкту (Non-Goals)
* Розподілені мережеві консенсуси (Raft/Paxos), реплікація або шардинг (система є суворо локальною).
* Транзакційні гарантії (ACID) для операцій над кількома ключами одночасно.
* Підтримка обсягу ключів, що перевищує розмір RAM (KeyDir повністю утримується в оперативній пам'яті).
* TTL / автоматичне старіння ключів, перелік ключів та діапазонні запити (SCAN).
* Hint-файли для прискорення старту (відновлення завжди читає сегменти повністю).
* Підтримка Windows (цільові платформи — macOS та Linux).

---

## 2. Архітектура системи (System Architecture)

Система складається з 5 ізольованих шарів, що взаємодіють між собою через Go-інтерфейси:

```text
+---------------------------------------------------+
|                 TCP Network Server                |
|      (Connection Limit & Text / RESP Protocol)    |
+---------------------------------------------------+
                          |
                          v
+---------------------------------------------------+
|               Engine (Façade API)                 |
|            PUT()  |  GET()  |  DELETE()           |
+---------------------------------------------------+
              |                           |
              v                           v
+---------------------------+ +---------------------+
|   KeyDir (In-Memory)      | | Storage Engine(Disk)|
|   • Hash Map Index        | | • Active Segment(W) |
|   • sync.RWMutex          | | • Inactive Seg.(R)  |
+---------------------------+ | • Compactor (Merge) |
                              +---------------------+
                                         |
                                         v
                              +---------------------+
                              | VFS(Abstraction L.) |
                              | OS FS / SimulatorFS |
                              +---------------------+

```

### 2.1. Специфікація модулів

Усі пакети розміщені в `internal/` (ідіоматичний для Go спосіб закрити пакети від зовнішнього імпорту); точка входу — `cmd/tinycask`.

* **TCP Network Server & Protocol Parser (`internal/server`):**
  * **Модель паралельності:** Goroutine-per-Connection. При надходженні підключення створюється окрема горутина. Кількість одночасних підключень обмежена (за замовчуванням 1024); неактивні підключення закриваються за таймаутом (5 хв).
  * **Протокол:** текстовий, сумісний із підмножиною RESP2.
    * *Inline-форма* — `<COMMAND> <KEY> [<VALUE>]\r\n` (зручна для `telnet`/`nc`; ключ і значення не можуть містити пробілів та `\r\n`).
    * *Binary-safe форма* — RESP-масив bulk-рядків із префіксами довжини (`*3\r\n$3\r\nSET\r\n$3\r\nkey\r\n$5\r\nvalue\r\n`); дозволяє довільні байти в значенні й робить сервер сумісним із `redis-cli` та `redis-benchmark`.
    * *Команди:* `PUT`/`SET`, `GET`, `DELETE`/`DEL`, `PING`, `COMPACT`, `INFO`, `QUIT`. Регістр команд не має значення.
    * *Відповіді:* `+OK`, bulk-рядок зі значенням, `$-1` (ключ не знайдено), `:1`/`:0` (результат `DELETE`), `-ERR <code> <message>`.
  * Парсер працює через буферизований читач (`bufio.Reader`) із жорсткими лімітами на довжину рядка, кількість аргументів і розмір bulk-рядка, захищаючи пам'ять від OOM при аномальних запитах.

* **Engine (Façade API, `internal/engine`):**
  * Єдина точка входу до сховища: `Open`, `Put`, `Get`, `Delete`, `Compact`, `Close`. Володіє блокуванням записувача, виконує відновлення при старті, фонову синхронізацію (fsync) та запуск Compactor.

* **KeyDir (In-Memory Index, `internal/index`):**
  * Потокобезпечна хеш-таблиця (`sync.RWMutex`), яка зберігає метадані розташування ключів у лог-файлах.

```go
type KeyDir struct {
    mu    sync.RWMutex
    index map[string]CommandIndex
}

type CommandIndex struct {
    FileID      uint32 // Ідентифікатор сегментного файлу
    ValueSize   uint32 // Довжина значення в байтах
    ValueOffset int64  // Абсолютний офсет початку Value у файлі
    Timestamp   uint64 // Час створення/оновлення запису
}

```

  * Офсет і розмір повного кадру обчислюються з цих полів: `RecordOffset = ValueOffset − 21 − len(Key)`, `RecordSize = 21 + len(Key) + ValueSize`.
  * `Timestamp` є суто інформаційним полем. Порядок записів визначається виключно парою `(FileID, офсет)`, оскільки системний годинник не є монотонним.

* **Storage Engine (`internal/storage`):**
  * **Active Segment:** Єдиний файл, відкритий у режимі Append (`O_APPEND | O_RDWR`): запис — тільки в кінець, читання — через `pread` (нещодавно записані ключі читаються саме з нього).
  * **Immutable Segments:** Закриті файли даних, доступні тільки для читання.
  * **Іменування файлів:** `seg_<ID>.data` — звичайний сегмент; `compact_<ID>.data` — результат злиття; `compact_<ID>.tmp` — незавершене злиття; `LOCK` — файл ексклюзивного блокування каталогу даних (захист від запуску двох процесів на одному каталозі). `ID` — монотонно зростаючий `uint32` (10 десяткових цифр у назві).
  * **Ротація:** коли Active Segment досягає ліміту (64 МіБ за замовчуванням), він синхронізується (`fsync`), стає Immutable, і створюється новий Active Segment з наступним ID.

* **Compaction Engine (`internal/compactor`):**
  * Фоновий процес, який зливає застарілі сегменти, відфільтровує видалені ключі й вивільняє дисковий простір.

* **Virtual File System (VFS Layer, `internal/vfs`):**
  * Абстракція над дисковими операціями для можливості підключення симулятора аварій. Дві реалізації: `OSFS` (реальна файлова система) та `SimulatorFS` (`internal/vfs/simfs`, файлова система в пам'яті з ін'єкцією збоїв). Увесь дисковий I/O ядра проходить виключно через VFS.

### 2.2. Формат зберігання даних (Binary Format)

Усі операції модифікації (PUT, DELETE) створюють бінарний кадр (Frame) у кінці Active-файлу. Дані ніколи не перезаписуються "на місці".

```text
+------------+---------------+----------+--------------+--------------+-----------+-------------+
| CRC32 (4B) | Timestamp(8B) | Type(1B) | Key Size(4B) | Val Size(4B) | Key (KB)  | Value (VB)  |
+------------+---------------+----------+--------------+--------------+-----------+-------------+
|<---------------------- Fixed Header (21 Bytes) -------------------->|<--- Dynamic Payload --->|

```

**Поля кадру** (усі числові поля — little-endian):

* **CRC32 (4 bytes)** — контрольна сума (поліном IEEE) для блоку `[Timestamp + Type + KeySize + ValSize + Key + Value]`.
* **Timestamp (8 bytes)** — nanoseconds Unix Epoch (інформаційне поле).
* **Type (1 byte)** — тип запису: `1` = PUT, `2` = DELETE (Tombstone). Будь-яке інше значення трактується як пошкодження.
* **Key Size (4 bytes)** — довжина ключа $K$ ($1 \le K \le 1024$).
* **Value Size (4 bytes)** — довжина значення $V$ ($0 \le V \le 1\,048\,576$).
* **Key** — $K$ байтів ключа.
* **Value** — $V$ байтів значення.

> **Маркер видалення (Tombstone):** При виклику `DELETE` створюється кадр із `Type = 2` та `Value Size = 0`. Завдяки окремому полю `Type` порожнє значення (`PUT key ""`) є легальним і не плутається з видаленням.

Формат має версію v1 і зафіксований golden-тестом; несумісна зміна формату потребує нового розширення файлів.

### 2.3. Алгоритми виконання операцій

#### Операція `PUT(Key, Value)`

1. Engine перевіряє ліміти розмірів, обчислює CRC32 та збирає бінарний Frame у пам'яті.
2. Під блокуванням записувача (`sync.Mutex`) Frame одним викликом `Write` додається в кінець Active Segment; за потреби перед цим виконується ротація сегмента.
3. **Не відпускаючи блокування**, після успішного I/O оновлюється запис у KeyDir (`FileID`, `ValueOffset`, `ValueSize`, `Timestamp`). Це гарантує, що порядок записів у лозі та порядок оновлень індексу збігаються (два паралельні `PUT` одного ключа не можуть розійтися).
4. Якщо `Write` завершився помилкою (зокрема частковим записом), Active Segment обрізається до останнього цілісного офсету, KeyDir не змінюється, клієнт отримує помилку. Якщо обрізання або `fsync` неможливі — Engine переходить у режим read-only (усі записи відхиляються, читання працюють).
5. Клієнту повертається відповідь OK.

#### Операція `GET(Key)`

1. Пошук запису в KeyDir під `RLock()`. Якщо не знайдено — повертається `ErrKeyNotFound`.
2. Отримуються `FileID`, `ValueOffset`, `ValueSize`; з них обчислюються офсет і розмір повного кадру (див. 2.1).
3. Виконується один системний виклик `pread(FileID, RecordOffset, RecordSize)`, що зчитує кадр повністю (Header + Key + Value).
4. Розраховується CRC32 і звіряється ключ. Якщо цілісність підтверджено — повертається `Value`; інакше — помилка `ErrCorrupt` (без `panic`).
5. Якщо сегмент щойно був видалений Compactor-ом (гонка між кроками 1 і 3), пошук у KeyDir повторюється — індекс уже вказує на новий файл.

#### Операція `DELETE(Key)`

1. Під блокуванням записувача перевіряється наявність ключа в KeyDir; якщо ключа немає — у лог нічого не пишеться, повертається «не знайдено».
2. У лог пишеться кадр-Tombstone (`Type = 2`, `Value Size = 0`).
3. Ключ видаляється з KeyDir у межах того самого блокування.

### 2.4. Алгоритм відновлення (Crash Recovery)

При запуску системи індекс KeyDir відбудовується з дискових логів за наступним алгоритмом:

```text
[Старт] --> [LOCK каталогу] --> [Видалення *.tmp та сегментів, заміщених compact_M]
                    |
                    v
       [Послідовне сортування сегментів за ID]
                    |
                    v
       [Читання файлу від Offset 0 до кінця]
                    |
                    +--> [Перевірка CRC32 кадру]
                    |            |
                    |            +-- [CRC OK] -------> [Оновлення KeyDir]
                    |            |
                    |            +-- [CRC BAD / Partial Write]
                    |                      |
                    |                      +-- [останній сегмент] --> [Обрізання битого хвоста]
                    |                      |
                    |                      +-- [не останній] -------> [ErrCorrupt, база не відкривається]
                    v
[Створення нового Active Segment]

```

Уточнення:

1. **Прибирання:** видаляються всі `compact_*.tmp` (незавершене злиття). Якщо існує `compact_M.data`, видаляються всі файли даних з `ID < M` — вони повністю заміщені результатом злиття (див. 2.5).
2. **Відтворення:** сегменти читаються за зростанням ID; кадр PUT оновлює KeyDir, Tombstone — видаляє ключ. Перед виділенням пам'яті довжини `KeySize`/`ValSize` перевіряються на ліміти.
3. **Битий хвіст:** неповний або пошкоджений кадр допускається лише наприкінці *останнього* сегмента (наслідок обірваного запису): файл обрізається до останнього цілісного кадру й синхронізується. Пошкодження в будь-якому іншому місці означає втрату вже підтверджених даних, тому база повертає явну помилку `ErrCorrupt` і не відкривається (fail-stop замість тихої втрати даних).
4. **Новий Active Segment** створюється з ID, на одиницю більшим за максимальний наявний.

### 2.5. Фонове злиття (Compaction) та усунення гонок з PUT/DELETE

Оскільки `PUT` та `DELETE` завжди пишуть виключно в Active Segment ($S_{active}$), фоновий процес Compactor працює за алгоритмом умовного оновлення індексу (Conditional Index Update), що виключає втрату нових даних:

1. **Ізоляція:** На старті Compactor під коротким блокуванням записувача закриває поточний Active Segment (ротація), резервує наступний ID $M$ для результату злиття й відкриває новий Active Segment з ID $M+1$. Вхідний набір — **усі** Immutable-сегменти ($ID < M$). Новий $S_{active}$ залишається повністю відкритим для паралельних записів клієнтів.
2. **Перенесення даних:** Compactor вичитує вхідні сегменти й копіює у `compact_M.tmp` тільки ті кадри PUT, які є актуальними за версією KeyDir (запис KeyDir вказує саме на цей кадр). Tombstone-и та застарілі версії не переносяться.
3. **Фіксація:** `compact_M.tmp` синхронізується (`fsync`), атомарно перейменовується в `compact_M.data`, після чого синхронізується каталог.
4. **Умовне оновлення KeyDir (Conditional Update):** Compactor бере короткотривалі блокування `KeyDir.Lock()` порціями (до 1024 ключів за одне блокування) і для кожного перенесеного ключа $K$ виконує перевірку:
   * Якщо `KeyDir[K].FileID` все ще вказує на один зі старих сегментів ($ID < M$) — координати ключа в KeyDir оновлюються на новий файл `compact_M.data`.
   * Якщо `KeyDir[K].FileID` вказує на новіший сегмент (під час злиття клієнт виконав новий `PUT`) або ключ відсутній (клієнт виконав `DELETE`) — перенесення для цього ключа скасовується, а запис у KeyDir залишається недоторканим.
5. **Очищення:** Старі файли ($ID < M$) видаляються з диска, каталог синхронізується.

**Інваріанти безпеки злиття:**

* Результат злиття з ідентифікатором $M$ заміщує *всі* файли з $ID < M$. Тому аварія між кроками 3 і 5 безпечна: при старті відновлення саме видалить заміщені файли (див. 2.4). Без цього правила відкинутий Tombstone міг би «воскресити» видалений ключ зі старого сегмента.
* Ідентифікатор $M$ менший за ID будь-якого сегмента, створеного після початку злиття, тому при відновленні новіші записи завжди відтворюються після перенесених.
* Одночасно виконується не більше одного злиття.

**Умова запуску:** автоматично — коли частка застарілих даних сягає порогу (див. 4.3), або вручну командою `COMPACT`.

### 2.6. Модель паралельності та синхронізації

| Ресурс / Компонент | Механізм захисту | Опис |
| --- | --- | --- |
| **KeyDir Index** | `sync.RWMutex` | Паралельні читачі (`GET`) беруть `RLock()`, записувачі (`PUT`/`DELETE`) беруть `Lock()`. Під цим блокуванням ніколи не виконується дисковий I/O. |
| **Active Segment** | `sync.Mutex` (блокування записувача) | Синхронізація послідовного додавання записів (Append) від багатьох паралельних TCP-горутин. Охоплює і запис у лог, і відповідне оновлення KeyDir. |
| **Immutable Segments** | Stateless `pread` + `sync.RWMutex` на наборі сегментів | Читання не блокують одне одного; kernel гарантує безпечне читання з файлового офсету. Блокування набору сегментів береться на запис лише на мить додавання/вилучення файлу. |
| **Compactor vs KeyDir** | Короткі `KeyDir.Lock()` порціями | Під час заміни сегментів Compactor оновлює `FileID` та `ValueOffset` для перенесених ключів порціями до 1024 ключів, щоб не блокувати `GET` довше за кілька мілісекунд. |

**Порядок захоплення блокувань:** блокування записувача → `KeyDir` → набір сегментів. Зворотний порядок заборонений.

### 2.7. Політика довговічності (Durability / fsync)

Запис кадру завжди виконується одним системним викликом `write` без буферизації в просторі користувача, тому підтверджений клієнту запис переживає аварійне завершення процесу (`kill -9`) за будь-якої політики. Стійкість до вимкнення живлення визначається параметром `sync`:

| Політика | Поведінка | Втрата при вимкненні живлення |
| --- | --- | --- |
| `always` | `fsync` після кожного запису, до відповіді клієнту | Немає (RPO = 0) |
| `interval` (за замовчуванням, 1 с) | фоновий `fsync` Active Segment за таймером | Не більше одного інтервалу |
| `never` | `fsync` лише при ротації, злитті та штатному завершенні | Залежить від ОС |

Незалежно від політики: сегмент синхронізується перед ротацією; результат злиття — перед перейменуванням; каталог — після створення, перейменування та видалення файлів. Помилка `fsync` вважається фатальною для запису: Engine переходить у режим read-only.

### 2.8. Ліміти та конфігурація за замовчуванням

| Параметр | Значення | Примітка |
| --- | --- | --- |

## 3. Стратегія та специфікація тестування (Testing Strategy)

### 3.1. Класифікація тестів (Test Taxonomy)

* **Unit Tests (White-Box):** Ізольоване тестування бінарного кодека, розрахунку CRC32 та потокобезпеки хеш-карти KeyDir.
* **Integration Tests (Gray-Box):** Перевірка взаємодії дискового двигуна, індексу KeyDir та фонового Compactor.
* **Fault Injection & Chaos Tests (Simulation):** Детерміноване тестування стійкості до відмов за допомогою симулятора файлової системи (SimulatorFS).
* **Fuzzing & Property-Based Tests (Black-Box):** Перевірка інваріантів та пошук граничних випадків парсерів за допомогою `go test -fuzz`.

### 3.2. Матриця покриття модулів (Test Coverage Matrix)

### 3.3. Деталізація сценаріїв Хаос-тестування (Fault Injection Specs)

Хаос-тести виконуються в пам'яті через абстракцію SimulatorFS, що робить їх детермінованими та миттєвими. SimulatorFS підтримує чотири види збоїв: помилка N-го виклику операції; обірваний запис на байті N з подальшою «аварією»; квота диска; втрата несинхронізованих байтів при перезапуску. Операції над каталогом (створення, перейменування, видалення) у симуляторі вважаються миттєво довговічними.

#### Сценарій 1: Partial Write / Partial Record Crash (Обрив запису при аварії)

* **Передумова:** Клієнт відправляє `PUT("user", "data")`. Симулятор диска перериває операцію запису `Write()` після того, як записав заголовок (Header), але до повного збереження Body.
* **Дія:** Процес перезапускається (Reboot). Викликається алгоритм відновлення індексу.
* **Очікуваний результат:**
  * Двигун зчитує неповний запис і виявляє його (кадр коротший за заявлену довжину або розбіжність CRC32).
  * Неповний запис ігнорується (обрізається хвіст файлу).
  * Індекс KeyDir відновлюється до останнього цілісного стану.
  * База продовжує коректну роботу без пошкодження попередніх даних.

#### Сценарій 2: Interrupted Compaction (Аварія під час прибирання сміття)

* **Передумова:** Процес Compactor зчитує 3 сегменти й пише відфільтровані дані у тимчасовий файл `compact_102.tmp`.
* **Дія:** Симулятор викликає аварію під час виконання запису у `.tmp` файл (до моменту атомарного Rename). Додатково перевіряється аварія одразу після Rename, до видалення старих сегментів.
* **Очікуваний результат:**
  * До Rename: початкові 3 сегменти залишаються недоторканими й активними; при наступному старті база виявляє неоформлений `compact_102.tmp` і видаляє його.
  * Після Rename: при старті база видаляє заміщені сегменти й працює з `compact_102.data`.
  * В обох випадках жоден актуальний ключ не втрачено і жоден видалений ключ не «воскрес».

#### Сценарій 3: Симуляція відсутності вільного місця (`ErrNoSpace`)

* **Передумова:** Налаштовано ліміт симулятора диска у 1 МБ. База заповнена на 999 КБ.
* **Дія:** Відправляється `PUT` розміром 10 КБ.
* **Очікуваний результат:**
  * Метод `Write()` повертає POSIX `ErrNoSpace` (можливо, після часткового запису).
  * Частково записаний кадр обрізається, запис у KeyDir не додається (операція атомарно відкочується).
  * Клієнту повертається чітка помилка `ERR no_space`.
  * Наступні `GET` і менші за розміром `PUT` працюють коректно.

### 3.4. Перевірка інваріантів та Фаззінг (Invariants & Fuzzing)

#### Інваріанти цілісності (Property-Based Verification)

Для будь-якого стану логу після відновлення повинні виконуватися математичні інваріанти цілісності:

$$\text{Count}(\text{KeyDir}) = \text{Count}(\text{Unique Non-Deleted Keys in Log})$$

$$\forall k \in \text{KeyDir}: \text{CRC32}(\text{pread}(k.\text{FileID}, \text{RecordOffset}(k), \text{RecordSize}(k))) == \text{Valid}$$

*Пояснення формули:* Кількість елементів в in-memory індексі KeyDir строго дорівнює кількості унікальних ключів у дискових сегментах, останнім записаним станом яких не є Tombstone (`Type = 2`); кожен запис індексу вказує на цілісний кадр.

Інваріанти перевіряються **модельним тестом**: генератор із фіксованим seed виконує випадкову послідовність `PUT`/`DELETE`/`GET`/`COMPACT` з аварією у випадковій точці, після чого стан відновленої бази порівнюється з еталонною моделлю (`map`). Підтверджені операції мають бути присутні; операція, перервана аварією, або застосована повністю, або не застосована зовсім.

#### Fuzz-тестування парсерів

* `go test -fuzz=FuzzParseFrame` — генерує мільйони псевдовипадкових байтових послідовностей на вхід TCP-парсеру.
* `go test -fuzz=FuzzDecodeRecord` — те саме для декодера дискових кадрів (саме він першим зустрічає пошкоджені дані при відновленні).
* **Мета:** Переконатися, що парсери ніколи не спричиняють `panic` або `out-of-memory` за будь-яких некоректних даних у мережі чи на диску.

### 3.5. Метрики та інструменти тестування

* **Тестовий фреймворк:** Стандартний `testing` + `github.com/stretchr/testify` (для `assert`/`require`).
* **Детектор гонок (Race Detection):** Усі інтеграційні та юніт-тести обов'язково проходять перевірку прапорцем `go test -race ./...`.
* **Покриття коду (Code Coverage):**
  * Загальний цільовий показник: $> 85\%$.
  * Покриття модулів Storage Engine, Recovery та Compactor: $\ge 90\%$, і кожна точка ін'єкції збоїв має бути виконана хоча б одним тестом. (Формальні $100\%$ рядків недосяжні через гілки обробки помилок, які неможливо викликати.)

## 4. Нефункціональні вимоги (Non-Functional Requirements)

### 4.1. Продуктивність, Затримки та Бенчмаркінг (Performance Specs)

Для оцінки деградації продуктивності під час фонового Compaction та на змішаному навантаженні встановлюються наступні цільові метрики. Вони вимірюються й публікуються у звіті (`BENCHMARKS.md`), але не є умовою проходження автоматичних тестів: вимірювання часу на ноутбуці та в CI нестабільні.

**Еталонні умови:** Apple M1 Pro, macOS, SSD; політика `sync=interval`; ключі 16 байтів, значення 256 байтів; 50 паралельних клієнтів.

| Сценарій навантаження | Метрика P99 Latency | Метрика Throughput | Метод вимірювання / Верифікація |
| --- | --- | --- | --- |
| **GET Only (100% Читання)** | $\le 1\text{ ms}$ | $\ge 20,000\text{ ops/sec}$ | Паралельні `pread` без блокування Active Segment |
| **PUT Only (100% Запис)** | $\le 4\text{ ms}$ | $\ge 12,000\text{ ops/sec}$ | Запис без `fsync` на кожну операцію (`sync=interval`) |
| **Mixed Workload (80% GET, 15% PUT, 5% DELETE)** | $\le 3\text{ ms}$ | $\ge 15,000\text{ ops/sec}$ | Симуляція реального профілю навантаження багатьох клієнтів |
| **Mixed Workload під час активного Compaction** | $\le 5\text{ ms}$ | $\ge 10,000\text{ ops/sec}$ | Вимірювання P99 під час активного злиття ~200 МБ даних на диску |

#### Порівняльний бенчмаркінг (Compaction vs Baseline)

Вимірювання проводяться на двох рівнях: `go test -bench` для Engine (з власною метрикою P99) та `redis-benchmark` для наскрізного вимірювання через TCP.

* **Baseline Test:** Вимірювання затримки P99 та пропускної здатності при вимкненому Compacting.
* **Stress Compaction Test:** Примусовий запуск фонового Compactor під підключеним змішаним навантаженням.
* **Цільовий критерій:** затримка P99 для GET операцій під час роботи Compactor не перевищує $5\text{ ms}$; зниження Throughput відносно Baseline — не більше ніж на $35\text{–}40\%$.

### 4.2. Надійність та Збереження даних (Reliability & Durability)

* **Recovery Point Objective:** Жоден підтверджений клієнту PUT-запит не повинен бути втрачений при штатному завершенні (`Ctrl+C`, SIGTERM) або аварійному завершенні процесу (`kill -9`) — за будь-якої політики `sync`. При вимкненні живлення RPO = 0 гарантується лише для `sync=always`; для `sync=interval` втрата обмежена одним інтервалом (див. 2.7).
* **Zero Corruption Propagation:** При пошкодженні байтів у кінці логу (Partial Write) система повинна атомарно відкотити нецілісний запис, ізолювати помилку та продовжити роботу без падіння процесу (`panic`).
* **Compaction Safety:** Фонове злиття файлів не повинно блокувати операції читання (GET) більше ніж на $5\text{ ms}$ ані в момент атомарного перейменування файлу `rename()`, ані під час оновлення індексу.
* **Single Writer:** Каталог даних одночасно може відкрити лише один процес (файл `LOCK`).

### 4.3. Використання ресурсів (Resource Efficiency)

#### Оверхед пам'яті для KeyDir (Memory Footprint)

Розмір індексу в RAM наближено обчислюється за формулою:

$$\text{RAMUsage} \approx N \times (\text{Len}(\text{Key}) + 48\text{ bytes})$$

де $N$ — кількість унікальних ключів. Формула не враховує накладні витрати хеш-таблиці Go, тому цільовий показник перевіряється вимірюванням: база повинна утримувати $1,000,000$ ключів (довжиною до 32 байтів) у межах $\sim 100\text{--}150\text{ МБ RAM}$. Під час злиття додатково тимчасово утримується список перенесених ключів (до ~50 МБ на мільйон ключів).

* **Дисковий оверхед (Disk Amplification):** Фоновий Compactor запускається, коли частка застарілих даних (Tombstones + старі версії) сягає $\ge 50\%$ від загального обсягу дискових сегментів. Частка обчислюється як $1 - \text{LiveBytes} / \text{DiskBytes}$, де `LiveBytes` — сумарний розмір кадрів, на які вказує KeyDir.

### 4.4. Обмеження реалізації (Maintainability Constraints)

* **Обсяг коду (Code Budget):** Ядро системи не перевищує 2500–3000 LOC (без тестів), що гарантує високу читабельність та простоту проведення коду-рев'ю.
* **Мінімальні зовнішні залежності (Zero-Dependency Policy):**
  * Для ядра та VFS використовувати виключно стандартну бібліотеку Go (`os`, `sync`, `net`, `encoding/binary`, `hash/crc32`, `syscall` — для блокування каталогу).
  * Зовнішні бібліотеки дозволені тільки для тестів (`github.com/stretchr/testify`).
  * Інструменти розробки (`golangci-lint`, `redis-benchmark`) не є залежностями коду.

## 5. Журнал змін відносно затвердженої версії 1.0

Архітектура (5 шарів, KeyDir + append-only лог, Compaction з умовним оновленням індексу, VFS із симулятором збоїв) не змінювалася. Версія 1.1 усуває знайдені під час аудиту помилки коректності та заповнює прогалини специфікації.

**Виправлення коректності**

| № | Було (v1.0) | Стало (v1.1) | Причина |
| --- | --- | --- | --- |
| 1 | Запис у лог і оновлення KeyDir захищені різними блокуваннями | Обидві дії виконуються під одним блокуванням записувача (2.3, 2.6) | Два паралельні `PUT` одного ключа могли залишити в індексі старішу версію; після рестарту значення «змінювалося» |
| 2 | Tombstone = `Value Size = 0` | Окреме поле `Type` (1 байт), заголовок 21 байт (2.2) | `PUT key ""` був невідрізненним від видалення |
| 3 | Ідентифікатор файлу злиття та порядок відтворення не визначені | Файл злиття отримує ID $M$, менший за всі новіші сегменти, і заміщує всі файли з $ID < M$ (2.4, 2.5) | Аварія між Rename і видаленням старих сегментів «воскрешала» видалені ключі; старі дані могли перекрити новіші |
| 4 | Після невдалого `Write` у лозі лишався частковий кадр | Обрізання до останнього цілісного офсету; при неможливості — режим read-only (2.3) | Наступні коректні записи опинялися за «сміттям» і губилися при відновленні |
| 5 | `GET` читає лише Value, але «перевіряє CRC» | `GET` читає повний кадр одним `pread`; офсет обчислюється з полів `CommandIndex` (2.1, 2.3) | CRC охоплює весь кадр; структура `CommandIndex` залишилася без змін |
| 6 | Оновлення KeyDir після злиття під одним `Lock()` | Порціями до 1024 ключів (2.5, 2.6) | Одне блокування на мільйон ключів триває десятки мілісекунд і порушує вимогу 4.2 |
| 7 | Поріг злиття «$\le 50\%$» | «$\ge 50\%$», визначено формулу (4.3) | Описка |

**Уточнення та заповнені прогалини**

* Визначено політику `fsync` і точне формулювання RPO (2.7, 4.2): у v1.0 «RPO = 0» суперечило «запису з буферизацією».
* Визначено поведінку при пошкодженні: обрізається лише хвіст останнього сегмента, інакше — явна помилка (2.4); у v1.0 блок-схема та матриця тестів суперечили одна одній («обрізати» проти «пропустити»).
* Active Segment відкривається `O_RDWR` (2.1): з `O_WRONLY` неможливо прочитати щойно записаний ключ.
* Описано гонку «`GET` проти видалення сегмента» та її розв'язання повторним пошуком (2.3).
* Протокол: збережено текстову форму `<COMMAND> <KEY> [<VALUE>]\r\n` і додано binary-safe форму RESP2 (2.1), що дає готові клієнт і генератор навантаження (`redis-cli`, `redis-benchmark`).
* Додано: ліміти розмірів, ротацію сегментів, іменування файлів, файл `LOCK`, graceful shutdown, ліміт підключень і таймаути (2.1, 2.8).
* Пакети перенесено з `pkg/` до `internal/`; фасад Engine отримав власний пакет `internal/engine`.

**Скорочення обсягу (щоб укластися в 3–4 тижні)**

* Сценарій «IO Timeout» замінено на загальну помилку запису/синхронізації (3.2).
* Вимогу $100\%$ покриття для Storage/Recovery замінено на $\ge 90\%$ плюс обов'язкове виконання кожної точки ін'єкції збоїв (3.5).
* Метрики продуктивності вимірюються і звітуються, але не блокують автоматичні тести; обсяг даних для тесту злиття зменшено з 1 ГБ до ~200 МБ; узгоджено суперечливі показники деградації (4.1).
* Абстрактні property-тести конкретизовано як один модельний тест із фіксованим seed; фаззінг розділено на два цільові тести (3.4).
